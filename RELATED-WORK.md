# Where This Fits (as of September 2026)

Is a stateless external model gating an agent's actions against a locked intent a novel idea? No — by September 2026 this is a widely recognized, increasingly standard pattern in agent security, not something invented here:

- **AI Control / trusted monitoring.** Research groups including Redwood Research frame this exact shape — a well-understood "trusted" model reviewing a more capable, potentially subversive "untrusted" agent's actions and deciding what to allow, flag, or block — as "trusted monitoring." Active 2026 work in the same space (Ctrl-Z, Bootstrapped Monitoring, Factor(T,U)) is refining the same core idea at frontier scale; NanCy implements a small, single-plugin version of it.
- **Intent-based guardrails.** Industry security literature now names this directly: continuously verifying an agent's actions against approved intent, before execution rather than after, appears in frameworks like Proofpoint's "Agent Integrity Framework – 2026 Edition" and the AgentDoG diagnostic framework, and in academic work like "The Alignment Gate: Intent and Instruction Guardrails for Agentic AI" (ESANN 2026).
- **A limitation this shares with everyone else's, not a NanCy-specific flaw.** LLM-as-judge intent verification has measured reliability limits — cross-model agreement on "intent resolution" scoring runs around 80%, meaning even well-designed judges disagree with each other roughly one time in five. Treat NanCy's verdicts as a strong signal, not ground truth — consistent with the "Pragmatism over Perfection" stance in the main [README](./README.md).
- **What's more specific here:** the stateless framing (no persisted conversation with the reviewer for an attacker to influence over multiple turns), the confirmation lock being *code-enforced* rather than merely prompted (the agent cannot write its own "confirmed" record — see feature #2 in the README), review of outbound messages as well as tool calls, a disposable worker session per confirmed task, and a two-stage browser write check that can reject the destination before disclosing the value to the reviewer. NanCy packages these choices as a small plugin for one specific agent framework (OpenClaw) rather than a general authorization platform.

**Closest concrete comparisons found so far:**

- **[Meta LlamaFirewall's AlignmentCheck](https://meta-llama.github.io/PurpleLlama/LlamaFirewall/docs/documentation/scanners/alignment-check)** scanner (open-sourced May 2025) is the closest match for the *semantic-review* half: a separate LLM reasons over an agent's action trace against the user's stated objective to catch goal hijacking from prompt injection or misleading tool output. The main structural difference is scope — it reasons over the whole trace it's given, while NanCy hands its reviewer a deliberately bounded slice each call (the confirmed task file plus a short recent-calls/reasoning window). Whether AlignmentCheck is stateless in the same sense NanCy is isn't something its public docs confirm either way.
- **[ClawGuard](https://github.com/Claw-Guard/ClawGuard)** is the closest match for the *task-confirmation* half, and happens to be an OpenClaw plugin too: `user states objective → ClawGuard derives task-specific access constraints → agent makes a tool call → ClawGuard's rule engine checks the call against those constraints`, ending in allow, deny, or pause-for-human-approval. The key difference: ClawGuard's actual allow/deny decision is rule-based (allowed commands, paths, domains) against constraints derived once from the goal, not a fresh LLM judgment of each action's semantics. NanCy is closer to the reverse — an LLM judgment against the locked task on (almost) every call, with rule-based checks reserved for the parts that should never depend on LLM judgment at all (Domain Border Control, protected-file writes).
- **[Continuous Agent Semantic Authorization (CASA)](https://arxiv.org/abs/2605.02682)** is a particularly close architectural comparison. It combines deterministic controls with a semantic layer that extracts the subject's intended task from a multi-turn conversation and checks proposed tools against it at an authorization server. This means the broad combination of deterministic enforcement and semantic task alignment is established prior art. NanCy makes different implementation choices: an explicit code-recorded confirmation instead of task extraction alone, a bounded fresh review for each action, and OpenClaw-specific session and message handling.
- **[Intent-Governed Access Control (IGAC)](https://arxiv.org/abs/2606.22916)** treats expressed user intent as a server-side authorization attribute. Its intent certificates, session-scoped policy narrowing, intent-aware tool manifests, and tool/payload consistency checks are a stronger formal authorization treatment of the same underlying problem. NanCy is narrower and lighter: it does not implement cryptographic certificates or monotonic capability narrowing, but anchors its semantic checks to a protected, expiring confirmation record inside an OpenClaw plugin.
- **[IntentGuard](https://openreview.net/pdf?id=kabNlhXQkT)** uses a Plan Gate and Tool Gate to compare both an agent's proposed plan and its tool calls with the original task. It preserves the user's raw prompt verbatim as the intent reference instead of relying on a model-generated rewrite. That is close to NanCy's protected anchor and per-action review, but it does not document NanCy's separate affirmative-confirmation record, outbound-message gate, or disposable worker lifecycle.
- **[NiyamAI](https://arxiv.org/abs/2608.07167)** locks permitted tools and constraints into a hashed Intent Contract at session start, then has an isolated Judge validate every tool call before execution and produces a verifiable proof of the judgment. This is the closest match found for NanCy's locked-intent-plus-independent-judge core, and is stronger on verifiability. Its published description does not include NanCy's code-mediated `y`/`yes` confirmation flow, outbound-message review, or main/worker session split.
- **[SARA](https://arxiv.org/abs/2608.27146)** constructs a task-level authorization contract from the user's original request and checks proposed calls against that authority root while tracking whether later actions were induced by untrusted tool output. Its persistent provenance tracking addresses multi-step prompt injection more directly than NanCy's short bounded history. It does not describe a separate user-confirmation record, outbound-message enforcement, or disposable task workers.
- **[CommonstackAI's ClawGuard](https://github.com/CommonstackAI/ClawGuard)** is the closest OpenClaw comparison for the LLM-review path: a separate small model compares destructive tool calls with the original user message at `before_tool_call`. It reviews only calls classified as destructive, while mutating calls pass without LLM review; NanCy aims to review nearly every tool call plus outbound messages and uses a code-owned confirmed-task record rather than passing the original message directly.
- **[Google ADK's plugin/callback system](https://google.github.io/adk-docs/plugins/)** (`before_tool_callback`) is the general-purpose version of the mechanism underneath both of the above, and NanCy: a hook that can inspect or block a tool call before it runs. ADK ships this as a framework primitive — a task-confirmation lock or an AlignmentCheck/NanCy-style semantic reviewer would have to be built on top of it, not out of the box.
- **[OpenClaw's native security controls](https://docs.openclaw.ai/releases/2026.8.1/security-and-privacy)** now bind approvals to the exact request, command, session, and operator; support per-session permission modes; and carry authority into delegated workers. These overlap substantially with NanCy's deterministic and worker-isolation layers, but OpenClaw does not provide NanCy's fresh semantic comparison of nearly every action and outbound message with one protected confirmed-task record.
- **Outbound-content guards such as [Raucle](https://github.com/epic28-ltd/raucle) and [Prisma AIRS for OpenClaw](https://github.com/cdot65/prisma-airs-plugin-openclaw)** intercept both `before_tool_call` and `message_sending`. They show that covering messages as well as tools is not unique by itself. Their documented checks focus on injection, unsafe arguments, data leakage, malicious content, and configured policies rather than continuously matching both channels to a code-owned confirmed task.

Put together: NanCy should be understood as a distinctive engineering composition, not as the invention of intent-based runtime authorization. It combines an AlignmentCheck-style semantic reviewer, a code-owned user-confirmed task anchor, deterministic policy boundaries, outbound-message review, and disposable task workers on OpenClaw's hooks. The individual ideas — and even the broader semantic-plus-deterministic architecture — have clear prior art; the value here is putting this particular set of controls into a compact, inspectable OpenClaw implementation.

**Best-of-our-knowledge claim, as of September 2026:** this review did not find another publicly documented implementation that combines all of the following in one OpenClaw plugin: a confirmation record written only by trusted code from the user's explicit reply, fresh bounded intent review of both tool calls and outbound messages, deterministic policy boundaries, and a disposable worker session per confirmed task. This is a scoped literature-and-project search result, not proof that no private, unpublished, or differently described implementation exists.

One recommendation that does come directly out of the AI-control literature: the reviewer model should be genuinely independent of the agent it's reviewing, to avoid correlated blind spots (or, in the adversarial framing, monitor/agent collusion). NanCy's `analysis` config has always been fully independent of whatever model runs the main OpenClaw agent — see [Reviewer model independence](./README.md#reviewer-model-independence) in the README — and now also warns at startup if the two appear to be the same model.
